# ConfigHub — Codebase Summary

*Reference notes for the final-year-project report. Scope: the completed supervised-learning pipeline that predicts a TSN Gate Control List (GCL) from a network scenario, and the Streamlit app built around it. Reinforcement-learning stubs found elsewhere in the tree are out of scope and are not described here.*

## 1. System overview

ConfigHub takes a description of a Time-Sensitive Networking (TSN) scenario — a topology of talkers, one switch and listeners, plus each talker's traffic streams (priority class, period, packet size) — and produces a per-device IEEE 802.1Qbv Gate Control List: for every talker and switch egress port, a sequence of gate-open windows that tile one cycle. The schedule is predicted by a trained GraphSAGE Graph Neural Network (GNN) rather than computed analytically. The predicted schedule is validated structurally (every node scheduled, well-formed bitmasks, positive durations, cycle coverage) and then rendered as NETCONF/YANG-shaped XML matching the `ieee802-dot1dc-sched-if` model, ready to hand to a real switch's configuration interface. The major stages are: **scenario capture (Topology Manager UI) → graph construction → GNN inference → structural validation → XML export (Configuration Generation UI)**. A separate, offline stage — OMNeT++ simulation, dataset curation, and model training — produced the checkpoints the app loads; that stage is not part of the live app but is documented here because it explains the model's design.

## 2. Pipeline / data flow

Tracing one example end to end, from raw simulation to a deployed schedule:

1. **OMNeT++ simulation (external to this repo).** `data_prep/Omnett_ini/*.ini` pairs a topology+workload config (e.g. `omnetpp_111_1.ini`, filename encoding talker/switch/listener counts and a stream "profile" from `reference.md`) with a swept GCL config from `data_prep/GCL_ini/*.ini` (filename encodes the TT interval/packet-size point being tested). Each is run via `opp_run -f omnetpp_XXX.ini -f gcl_YYY.ini -c Batch_XXX -r 0..24`, sweeping TT7 interval × packet size (5×5 = 25 runs per config). Scalar/vector recording is enabled in the `.ini` (`**.scalar-recording = true`), so each run produces OMNeT `.sca`/`.vec` result files.
2. **Result extraction → dataset JSON.** The `.sca`/`.vec` files are converted into the run-record JSON schema described in §5 (`topology`, `workload`, `gcl`, `performance`). **No script in this repository performs that conversion** — it is an external/manual step, and its absence is a real gap in the current codebase (see §4). The output lands as `*_datasets.json` files under `data_prep/JSON/` (e.g. `protoN11-8k_datasets.json`), one list of run objects per config family.
3. **Quality filtering — `data_prep/filter_quality.py`.** Loads all `*_datasets.json` in a folder and splits runs into `quality_datasets.json` (kept) and `infeasible_datasets.json` (dropped) using a per-gate `deadline_miss_ratio` threshold (§4). Produces `protoN11-8k-filtered_datasets.json`, the dataset actually used for training.
4. **Merge/de-dup — `data_prep/data_manager.py`.** A standalone Streamlit tool for inspecting datasets (tables/charts of delay, throughput, deadline-miss ratio) and merging two dataset files into a `master_<timestamp>_<n>.json`, skipping duplicate `run_id`s. Not required for training (`gnn_model.py` can load a folder of files directly) but the recommended way to consolidate before a big training run.
5. **Graph construction — `src/layers/inferenceService/graph_builder.py`.** `build_graph(run)` turns one run dict into a `torch_geometric.data.Data` object: a 14-float feature vector per node, a 4-float label per node (from the ground-truth `gcl` block), and bidirectional edges from `topology.edges`.
6. **Training — `src/layers/inferenceService/gnn_model.py`.** `train()` loads every run, splits by `config_id` into train/val/test, builds a graph per run, and trains a 2-layer GraphSAGE network (`GraphSAGENet`) with MSE loss (§3) against the `gcl` labels. The best-validation checkpoint is saved as a `.pt` file, then manually moved into `src/layers/inferenceService/models/` with a matching entry added to `models/index.md`.
7. **Inference — Configuration Generation page.** A user builds (or imports) a topology/workload in the Topology Manager, then `ConfigController.build_run()` (`src/controllers/config_controller.py`) assembles the same run-shaped payload (with an empty `gcl`), `gnn_model.predict()` runs the chosen checkpoint over it, and the softmax gate-fractions are converted to nanosecond durations, snapped to a 50 µs hardware granularity and floored to at least one packet's transmission time.
8. **Validation — `ConfigController.validate_gcl()`.** Structural checks: all expected nodes scheduled, 4-bit bitmasks, positive durations, per-node total within 5% of the cycle time.
9. **XML export — `src/layers/ieeeService/netconf_yang.py`.** `gcl_to_xml()` renders the predicted GCL as `<interfaces>/<interface>/<gate-parameter-table>` XML per the `ieee802-dot1dc-sched-if` YANG model; `validate_xml()` confirms it re-parses. The result is downloadable as `config.xml` (and the raw prediction as `gcl.json`) from the Configuration Generation page.

## 3. Per-component summary

### `graph_builder.py` — run dict → PyG graph
- **Purpose:** deterministic, stateless conversion of one dataset run into model-ready tensors.
- **I/O:** input is a run dict (`topology`, `workload`, `gcl`); output is a `Data` object with `x` (`[N, 14]`), `edge_index` (`[2, 2E]`, bidirectional), `y` (`[N, 4]`), and a `node_type` tensor (0=talker, 1=switch, 2=listener).
- **Node/edge definition:** nodes are devices, named and ordered deterministically as talkers (`T1..Tn`) → switches (`S1..Sm`) → listeners (`L1..Lk`); edges are the physical links from `topology.edges`, duplicated in both directions so message passing is symmetric.
- **Feature vector (14 floats):** `total_load, tt7_load, tt6_load, tt5_load, be_load, tt7_period_norm, tt7_pkt_norm, tt6_period_norm, tt6_pkt_norm, tt5_period_norm, tt5_pkt_norm, be_period_norm, link_dr_norm, num_q_norm`. Periods are normalised by the cycle time, packet sizes by 1500 B, link rate by 1000 Mbps, queue count by 8. Every priority class except `BE` gets its own load/period/packet-size triple; `BE` gets load + period only (no packet-size feature) — it's treated as filler traffic, not a scheduled class with a hard timing budget.
- **Label vector (4 floats):** fraction of the cycle each of the 4 hardware gates is open, computed by summing `duration_ns` over every `gcl_sequences` entry whose 4-character `gate_bitmask` has that gate's bit set, then dividing by `gcl_cycle_time_ns`. Listener nodes get an all-zero label (they are never scheduled) and are excluded from the training loss via the `node_type` mask.
- **Design decisions:** switch nodes get an *aggregated* feature vector (loads summed across all talkers feeding it; period/packet-size taken from whichever talker has each type first, since these are constant per stream class in the dataset) rather than one switch-node-per-egress-port — this keeps the graph small and lets the switch's own prediction be a genuine consequence of message passing rather than a copy of one talker. A switch's egress `port_id` (e.g. `S1P1`) is looked up from `topology.edges`, falling back to `f'{sid}P1'` if not present, so the label lookup and the inference-time output share one node-naming convention.

### `gnn_model.py` — model, training loop, checkpoint I/O, inference
- **Architecture — GraphSAGE, 2 layers:** `conv1 = SAGEConv(in_channels, hidden_channels)` → ReLU → `conv2 = SAGEConv(hidden_channels, out_channels)` → `softmax(dim=1)`. Defaults are `in_channels=14, hidden_channels=64, out_channels=4`, but the actual shape used to reconstruct a given checkpoint is read from `models/index.md` (via `models.get_architecture()`), because checkpoints trained at different points in the project's history use different widths (64 vs 128) and, for the earliest one, a different input size (10, from a since-changed feature vector).
- **Softmax output:** the final layer produces 4 raw scores per node that are forced to sum to 1 across the 4 gates — this *is* the model's prediction: "what fraction of the cycle should gate *i* be open for this node," directly comparable to the label vector.
- **Training:** MSE loss between predicted and label fractions, computed only over non-listener nodes (masked by `node_type`). Adam, `lr=5e-4`, 200 epochs, batch size 32 (full-graph-per-sample mini-batches via PyG's `DataLoader`). A **predict-the-average baseline** (mean label over the training set) is reported alongside validation/test MSE every 10 epochs so a run that fails to beat "always guess the average" is visible immediately, not just a shrinking-loss number.
- **Train/val/test split by `config_id`, not by row** (70/15/15 of *configs*, seeded): a config's ~25 rows come from an OMNeT parameter sweep (interval × packet size) and are near-duplicates of each other, so a row-level split would leak near-identical siblings across the split and inflate the reported test accuracy. Falls back to a row-level split only when fewer than 3 distinct configs are available (e.g. training on a single per-config file).
- **Inference (`predict()`):** loads the requested checkpoint with its documented architecture, runs the graph through the model, then converts each node's 4 fractions into a GCL: `fraction * cycle_ns` is snapped to the nearest 50,000 ns (`_SNAP_GRANULARITY`, a stand-in for hardware gate-timer resolution), floored to at least the time needed to transmit the largest single packet seen in the run (`_max_pkt_tx_ns`) so a gate is never opened for a duration too short to send anything, and zero-duration windows are dropped from the output sequence.

### `models.py` — checkpoint/architecture metadata
- Parses `models/index.md` (a per-checkpoint Markdown record of `in_channels`/`hidden_channels`/`out_channels` plus `lr`/`epochs`/`batch_size` and a human description) and exposes `get_architecture(model_id)` and `list_models()`.
- **Design decision:** decouples "which checkpoint" from "what shape" — rather than hard-coding one `GraphSAGENet` shape and letting mismatched checkpoints crash `load_state_dict`, every checkpoint's shape is looked up by filename stem, with a warning-and-default fallback for undocumented checkpoints. This is what lets the six shipped checkpoints (a 10→64 sanity model, four 14→64 models from an interval/dataset/learning-rate sweep, and one 14→128 capacity experiment) all load side by side from the same UI dropdown.

### `netconf_yang.py` — GCL → NETCONF/YANG XML
- `gcl_to_xml(run, gcl)` builds one `<interface>` per scheduled node (talker or switch egress port), each containing a `<gate-parameter-table>` (namespaced to `ieee802-dot1dc-sched-if`) with an `<admin-control-list>` of `<gate-control-entry>` items (index, a fixed `sched:set-gate-states` operation name, the bitmask reinterpreted as an integer `gate-states-value`, and `time-interval-value` in ns) and an `<admin-cycle-time>` expressed as a numerator/denominator-over-1e9 fraction. `validate_xml()` just re-parses the string and reports whether it's well-formed.
- **Design decision:** the XML is derived purely from the model's own `gcl` output structure (`parent_id`, `gcl_sequences`) — it does not read `pcp`/`gate_id` back out of the workload, so exported schedules are fully determined by the GNN's prediction, not by any per-stream field a user set in the UI (see §4 limitations).

### `data_prep/filter_quality.py` — dataset quality gate
- CLI script: `is_quality(run)` keeps a run only if it has at least one "active" gate (`pkts_sent > 0`) and every active gate's `deadline_miss_ratio` is within a **per-priority threshold**: TT7 ≤ 2%, TT6 ≤ 5%, TT5 ≤ 10%, BE ≤ 99% (i.e. effectively unconstrained). Splits input into `quality_datasets.json` and `infeasible_datasets.json`, renumbers `run_id` in each, and prints a per-config kept/dropped breakdown plus delay statistics so a config that's infeasible at every sampled point is easy to spot.
- **Design decision:** the threshold is tiered by priority rather than a single global cutoff, because that mirrors the actual QoS contract of a TAS-shaped TSN network — a schedule that drops 8% of TT7 traffic is a bad training example even if its overall miss rate looks fine, whereas an 8% BE miss rate is unremarkable.

### `data_prep/data_manager.py` — dataset inspection/merge tool
- Separate Streamlit app (not part of the main app's navigation). Flattens each run into one summary row (streams, bandwidth, delay, deadline-miss ratio, throughput) for tabular/chart inspection, then merges a "new" file into a "master" file, skipping runs whose `run_id` already exists in the master, and writes a timestamped `master_<ts>_<n>.json`.

## 4. Key design decisions and rationale

| Decision | Reason |
|---|---|
| **Graph = devices as nodes, physical links as edges** | GCL scheduling is inherently a per-egress-port decision shaped by the traffic converging on it; message passing over the real topology lets a switch's prediction be informed by its neighbouring talkers' traffic, rather than treating each node's schedule as an independent regression. |
| **14-float node feature vector, split by priority class** | Mirrors the three factors a human TSN engineer reasons about per traffic class — how much load, how urgent/periodic, how large the packets are — for each of TT7/TT6/TT5 individually, plus a coarser load+period pair for BE (no packet-size feature, since BE has no timing budget to protect). Node *role* (talker/switch/listener) is carried structurally by graph position rather than a one-hot feature. |
| **GCL encoded as single-gate-per-window sequences summing to the cycle** | Matches real IEEE 802.1Qbv semantics (one traffic class's gate open per window) and lets the model output a 4-way softmax — durations are fractions of the cycle by construction, so a valid schedule always tiles the cycle rather than needing a separate normalisation/repair step. |
| **Per-priority feasibility filtering before training (`filter_quality.py`)** | A single global deadline-miss threshold would let through runs where the switch is already failing its highest-priority traffic; tiering the threshold by class (strict for TT7, lax for BE) keeps the training label distribution restricted to schedules that were actually *good*, not merely "not terrible on average." |
| **Train/val/test split by `config_id`, not by row** | Each config in the raw dataset contributes ~25 near-duplicate rows from an OMNeT parameter sweep; splitting by row would put siblings of test rows into training, letting the model "peek" and reporting an inflated accuracy that says nothing about generalisation to unseen scenarios. |
| **MSE-on-durations as the training signal, not the measured `deadline_miss_ratio`** | Training directly against `performance.deadline_miss_ratio` would require differentiating through the OMNeT++ simulator, which isn't available; MSE against the known-good GCL durations is used as a proxy, on the assumption that a schedule close to a feasible one (in duration terms) is itself feasible. **Limitation:** this proxy is not verified — nothing in the loss function guarantees a low-MSE prediction actually keeps any class's simulated miss ratio under threshold on a topology unlike anything in training; the guarantee only really holds for the filtered training distribution itself. |
| **Per-checkpoint architecture metadata (`models/index.md` + `get_architecture()`)** | The model's input/hidden width changed twice over the project's life (10→14 features, 64→128 hidden channels); rather than retraining every historical checkpoint to one fixed shape, each checkpoint records its own shape so all of them remain loadable from a single code path. |

**Other known limitations worth noting in the report:**
- Only the single-switch `TsnIntelStar` star topology is exercised end-to-end; `graph_builder`'s switch-aggregation logic and one-port-per-switch assumption are not validated against multi-switch topologies.
- `_stream_features()` looks up streams by the literal type strings `TT7`/`TT6`/`TT5`/`BE`; a stream typed `AVB` (offered as an option in the Topology Manager UI) still contributes to `total_load` but gets no dedicated period/packet-size feature.
- If a talker has two streams of the same `type`, `graph_builder.build_graph()`'s per-talker lookup (`{s['type']: s for s in entry['streams']}`) keeps only the last one — the other is invisible to that node's feature vector, including its contribution to `total_load`.
- `pcp` and `gate_id` are collected in the workload schema and shown in the UI, but are never read by `graph_builder.py`, `gnn_model.py`, or `netconf_yang.py` — gate assignment is entirely a function of the model's own softmax output, not of any per-stream field a user sets.
- The `.sca`/`.vec` → dataset-JSON extraction step has no corresponding script in this repository; it is assumed to happen externally, upstream of `data_prep/JSON/`.

## 5. Data schema

Each `*_datasets.json` file is a JSON list of **run** objects, each with a `run_id`, a human-readable `config_id`, and up to four parts:

| Part | Role |
|---|---|
| `topology` | model input — graph structure and hardware parameters |
| `workload` | model input — per-talker traffic streams |
| `gcl` | model output / training label — the gate schedule |
| `performance` | evaluation/filtering signal — measured simulation outcome, **not** fed into the training loss |

**`topology`**: `topology_id` (shape identifier; only `"TsnIntelStar"` supported end-to-end), `num_talkers`/`num_switches`/`num_listeners` (node counts, named `T*`/`S*`/`L*`), `link_datarate_Mbps`, `device_model` (informational), `num_tx_queues` (expected to be 4 — the model always predicts 4 gates), `gcl_cycle_time_ns` (schedule period, used to normalise/denormalise durations), and `edges` (directed `{from, to, port_id?}` list; a switch→listener edge's `port_id`, e.g. `"S1P1"`, is the node name used for that switch's schedule).

**`workload`**: one entry per talker — `talker_id`, `switch_id`, `listener_id`, `num_streams`, `total_bandwidth_Mbps`/`total_load_ratio` (precomputed sums), and a `streams` list. Each stream has `stream_id`, `type` (`TT7`/`TT6`/`TT5`/`BE`/`AVB`), `pcp`, `gate_id`, `period_ns`, `packet_size_bytes`, and derived `bandwidth_Mbps`/`load_ratio` (`packet_size_bytes*8/(period_ns*1e-9)/1e6`, divided by link rate).

**`gcl`**: one entry per scheduled node (`parent_id` = a talker ID or a switch egress `port_id`) with a `gcl_sequences` list of `{sequence_index, gate_bitmask, duration_ns}` — `gate_bitmask` is a 4-character `"ABCD"` binary string (one bit per hardware gate), exactly one bit set per window in this model, and a node's durations should sum to within 5% of `gcl_cycle_time_ns`.

**`performance`**: one entry per `{listener_id, port_id}` pair with a `metrics` list, one per hardware gate (0–3), each carrying `pkts_sent`/`pkts_received`/`pkts_loss_count`, `delay_max_us`/`delay_mean_us`/`delay_stddev_us`, `deadline_ns`, `deadline_miss_ratio`, `throughput_Mbps`, and `queue_max_length`. This block is what `filter_quality.py` reads to decide whether a run is "quality" or "infeasible," and what `data_manager.py` aggregates for its inspection charts — it plays no role in `gnn_model.train()`'s loss computation.
